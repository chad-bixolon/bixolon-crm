# Hosted CI v1

GitHub Actions runs `.github/workflows/ci.yml` on pull requests targeting `main` and pushes to `main`. Feature branch pushes by themselves do not run CI, avoiding a second run for commits already covered by a PR. A newer PR run cancels the older run for that PR; a new main push does not cancel an earlier main validation. The workflow has repository `contents: read` permission only. It uses GitHub maintained checkout, setup-node and upload-artifact actions, with npm download caching keyed by `app/package-lock.json`. It does not cache `node_modules`, generated Prisma code, a database, or build output.

The standard job fetches the candidate baseline so `git diff --check` covers committed PR changes (or all commits in a main push), as well as any build-generated working-tree changes.

| Status check / job | PR | Main push | What it validates |
| --- | --- | --- | --- |
| **Standard CI** | Always | Always | Node/lockfile/Dockerfile pin, `npm ci`, Prisma generation and normalized generated-client alignment, lint, TypeScript, complete `npm test`, one-worker Chromium release smoke, production Webpack build, `git diff --check` |
| **Migration validation** | When Prisma schema, config, migrations, migration harness/fixtures, generation helper, migration image inputs, npm manifest/lockfile, or this workflow change; otherwise the job reports success with its expensive step skipped | Always | Existing `npm run test:migrations` image and `scripts/test-migrations.py`: fresh replay, populated upgrade/preservation, integrity, schema parity, rollback/compatibility checks |
| **Production Docker build** | Runtime/build/security changes; documentation/test-only PRs skip expensive steps | Always | Final production target of `app/Dockerfile`; inspect Node 22.23.4 / Prisma 6.19.3 and scan the same final image with Trivy |

`app/.nvmrc` fixes Node at **22.23.4**. `ci:preflight` checks the running version, `app/package.json`, lockfile Prisma 6.19.3 versions and both Docker base images before installing dependencies. The standard job uses `npm ci`; its postinstall and the explicit generation step both use the existing safe Prisma helper. The alignment step reuses the release checker's normalized schema, generated schema, embedded runtime and version comparison. The Standard CI production build uses `npm run build:release`, which is the same `npm run build -- --webpack` path as local release validation.

The main-only Docker job builds the existing deployment Dockerfile unchanged. Its internal build command is currently `npm run build` (Next.js Turbopack); the separate Standard CI step verifies the release checker's Webpack build. Any Dockerfile builder change would also affect the DigitalOcean image and deserves a separate deployment review.

`npm test` runs every tracked unit/regression file with the existing two-file worker bound. Its one SQL fixture test remains opt-in. CI sets `SALESHUB_TEST_USE_CI_FIXTURES=true`, so import regression tests use the tracked, synthetic CSV and workbook pack in `tests/fixtures/ci-source/`. These files exercise the same parser paths and source layouts without including customer or commercial source documents. The pack is generated by `node tests/fixtures/ci-source/generate.mjs`; review fixture and expectation changes together. Local `release:check` continues to use ignored `reference-data/` files when available, including the real source workbook assertions. The synthetic pack is excluded from production Docker context.

## Isolated database and integrations

The standard job starts a fresh PostgreSQL 17 service with fixed test-only `saleshub_e2e` credentials. It maps the service to localhost port 55432, as required by the existing E2E auth guard. `SALESHUB_E2E_EXTERNAL_POSTGRES=true` tells `e2e/prepare.mjs` to use that service in CI; local runs still start the dedicated Compose database. The prepare script checks the expected database identity, creates `saleshub_e2e_release`, runs migrations and seeds fixtures. The web server uses guarded local E2E authentication, a fixed test token, mock Gmail and test storage. Standard lint, unit and build steps get a deliberately unusable localhost `DATABASE_URL`; the browser step replaces it with the fixed E2E URL internally. There is no route to a production database, object store, Gmail, Calendar or DigitalOcean. The full migration harness creates its own temporary PostgreSQL 17 Docker container on an internal network and removes its own resources.

**GitHub repository secrets required: none.** Placeholder auth values and database credentials are test-only. Do not add production OAuth, Support Gmail, Spaces, database or DigitalOcean credentials to this workflow. `prisma migrate deploy` appears only inside test database setup and the disposable migration harness; CI does not deploy a production migration. Chromium alone is installed with its Linux dependencies. The smoke command has one worker and zero retries. It does not run the broad browser suite or enable development impersonation. Run focused browser specs locally for changed features; add a separate sharded/browser job only after measuring runner memory, ports and fixture isolation.

## Local release check and drift

From `app/`, developers continue to run `npm run release:check -- --base <last-deployed-commit>` on a clean committed candidate. It remains the authoritative local release-validation command and produces private local evidence in `app/reports/release/`. It chooses migration replay for changes to the schema, migration harness, Prisma generation, migration image inputs, npm manifest/lockfile, or CI workflow. CI runs the underlying checks in visible steps because GitHub checks out a synthetic PR merge commit, has a different baseline, and stores step logs itself. The two paths share `test:migrations`, `test:e2e:release-smoke` and `build:release` scripts, the Prisma alignment function, and the same lint, typecheck and bounded `npm test` entry points. `tests/ci-contract.test.mjs` runs in the unit suite and fails if those required CI gates or shared scripts disappear. When changing a release gate, update both paths, this table and the contract test in one review.

The local checker enforces a clean candidate and writes a READY/NOT READY report. GitHub CI validates a fresh checkout and reports job statuses. Neither substitutes for **Administration → System Health → Deployment Status** after production deployment: confirm deployed SHA, migration currency, schema/client compatibility and health there, plus provider/scheduler checks from the release checklist.

## Failure evidence and troubleshooting

Each named step retains its normal GitHub Actions log. On a standard job failure, the workflow uploads Playwright `test-results` and the HTML report if present; on a migration failure it uploads the captured migration log. Artifacts expire after seven days and are not uploaded on success. No environment dump, database export, production credential, or built image is uploaded. If installation fails, inspect the `npm ci` log and lockfile; if Prisma fails, inspect generation/alignment before debugging tests; if browser setup fails, check the PostgreSQL service health, the fixed port and Chromium library installation; if migration replay fails, inspect the migration log and review SQL/fixtures. Run `npm run test:migrations` locally when Docker is available. A failed unit test fails CI immediately; CI never retries units. Playwright's CI default retry is overridden to zero by the shared smoke script.

Recent warmed local release checks took roughly **10–12 minutes** without migration replay; recent local migration stages took **20–25 minutes**. Budget about **15–30 minutes for Standard CI** on a cold runner, **20–35 minutes for migration validation** and **5–15 minutes for the main-only Docker build**. The initial CI PR runs migration validation because it changes this workflow. These hosted figures are planning estimates, not measured Actions results. Browser dependency installation, unit tests and Next.js builds are likely the largest standard steps; migration replay and Docker's two `npm ci` layers dominate full-release minutes. Record actual job durations after the first PR and main run and revise these figures. Main jobs run concurrently, so elapsed time is less than the sum of runner minutes.

## Branch protection and deployment boundary

After this workflow is merged and has run, a repository Admin should protect `main` with pull requests before merge if that fits the team, and require the exact status checks **Standard CI** and **Migration validation**. Requiring an up-to-date branch is useful when concurrent merges are common, but may add reruns. **Production Docker build** runs only on main, so do not require it for PR merge. If the repository's GitHub plan or ruleset UI does not offer required checks, use the available branch protection option and review these two Actions jobs manually before merge. Do not modify repository settings from CI.

The intended flow is **PR → GitHub CI → merge to main → DigitalOcean auto-deploy**. A main push also runs full CI and the production Docker build as independent release evidence. DigitalOcean may start deployment as soon as main changes; this v1 workflow does not gate or trigger its auto-deploy. The existing DigitalOcean migration/deployment handling is unchanged. GitHub Actions does not call the DO API, push an image, deploy, restart production, or run a production migration.

## Security scanning

Dependency & Container Security v1 adds scoped dependency audits, scanning of final production/operations images, weekly rescanning, SARIF and CycloneDX evidence. It preserves existing checks and applies a documented severity/exposure policy rather than a blanket npm High gate. The fresh 2026-10-29 app and recovery lockfile audits report zero vulnerabilities; historical October results are superseded. Image findings remain, including one fixed Critical operations-image blocker.
