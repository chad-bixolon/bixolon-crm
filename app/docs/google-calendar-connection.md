# Google Calendar connection and event sync (v1, Steps 1–2)

## Architecture

SalesHub uses `next-auth` 5.0.0-beta.32 (Auth.js), the built-in Google provider, and JWT sessions. Normal sign-in asks for `openid email profile`; it does not ask for offline access, and it does not persist an OAuth access or refresh token. `ExternalIdentity` stores the Google issuer and subject linked to a pre-created CRM `User`. There is no Auth.js adapter `Account` row. The Auth.js callback remains `/api/auth/callback/google`.

Calendar uses a separate user-initiated incremental-consent flow at **My integrations** (`/my-integrations`). The sole Calendar permission is `https://www.googleapis.com/auth/calendar.events.readonly`, which allows reading events on the user's calendars for a later Activity review. It does not allow editing events. The authorization request also includes `openid email profile` to verify that the consenting Google subject matches the signed-in Google identity. It sets `include_granted_scopes=true`, `access_type=offline`, and `prompt=consent`. Consent prompting seeks a refresh token for background use; Google can omit one on reconnect, so the existing encrypted refresh token is retained only for the same Google subject. A first connection after disconnect requires a new refresh token.

The flow starts in a server action. A signed, random, ten-minute OAuth state is stored in an HTTP-only, same-site cookie scoped to `/api/calendar/callback`; the callback checks it against the real authenticated CRM user and deletes it after one use. The callback exchanges the code on the server, reads Google's userinfo, verifies the Google subject against the user's existing `ExternalIdentity`, and stores credentials in `GoogleCalendarConnection`. It accepts no browser-supplied user ID. Failed consent or callback validation leaves any previous connection untouched. The callback and connection actions use `getRealAuthenticatedUser`, not the development impersonation effective user. Admins can connect only their own Calendar while impersonating another CRM user. CRM permissions are unchanged.

There is one Calendar connection per user and one owner per Google subject. The table stores the Google subject/email, encrypted refresh token, granted scopes, status (`CONNECTED` or `NEEDS_REAUTH`), last connected time, and a non-secret error description. Access tokens are short-lived and never persisted. A server-only refresh helper returns an access token in memory; invalid or revoked credentials set `NEEDS_REAUTH` without touching the Auth.js login. The status page selects only non-secret columns. Disconnect deletes the connection row and its credential without changing the normal Google sign-in link. Google token revocation is deliberately not called because the shared OAuth client uses incremental authorization and revocation could affect the user's sign-in or other grants.

The refresh token is encrypted with AES-256-GCM using a random 96-bit nonce and authenticated context. Set `CALENDAR_TOKEN_ENCRYPTION_KEY` to **32 random bytes encoded as exactly 64 hex characters** (for example generate with `openssl rand -hex 32`); store it as an encrypted DigitalOcean runtime secret. Do not reuse `AUTH_SECRET`. Keep the key available across deployments; rotating it requires re-encrypting existing rows or having users reconnect. Tokens are never placed in client props, ordinary actions, pages, logs, or test snapshots.

## Personal time zones and timestamp policy

`User.timeZone` stores an IANA identifier, not a fixed abbreviation such as EST or PST. The new `20261007130000_user_time_zone` migration adds a required field with `America/New_York` as the database and Prisma default. Existing users receive that default; new users receive it until they choose another zone in **My integrations → Personal settings**. Users can save only their own setting, including when an Admin is using development impersonation. The real authenticated identity owns both the setting and the Calendar connection. Browser detection never overrides the saved choice.

PostgreSQL timestamp values continue to represent UTC instants. The shared `formatDateTimeForUser` formatter uses the viewer's saved IANA zone and `Intl.DateTimeFormat` for personal UI timestamps and daylight-saving changes. My integrations uses it for Calendar connection and sync timestamps. Future Calendar event review and matching should use the viewer's zone for timed event display; all-day events remain date-only with Google's exclusive end-date semantics. Sync retains UTC instants, Google's original time-zone metadata and original recurring start value. Changing a display zone never rewrites Calendar data.

Shared business dates remain governed by their existing explicit `America/New_York` rules. In particular, Price Exception expiration, notification evaluation, forecast snapshots, and management reporting must not be changed by a user's display preference. Some existing pages use Eastern time for date presentation as well as business grouping; each should be classified before later incremental UI conversion. Tasks, Activities, Opportunity History, notifications, PE history, audit history and Calendar review are possible future consumers of the personal formatter, outside this step.

## Google Cloud and deployment setup

1. Enable the Google Calendar API in the existing Google Cloud project. Configure the OAuth consent screen to declare `https://www.googleapis.com/auth/calendar.events.readonly` and review its sensitivity classification in the console. The existing web OAuth client ID and secret can be reused; a second client is not needed for this design.
2. Add the **exact** Calendar callback URI to that client's authorized redirect URIs: `http://localhost:3000/api/calendar/callback` for localhost development, and `https://<actual-production-host>/api/calendar/callback` for production. Keep the existing `/api/auth/callback/google` entries. `AUTH_URL` must equal the browser origin, with no path. The current raw LAN-IP development URL is not a valid Google web OAuth redirect; use the documented localhost tunnel or HTTPS development hostname.
3. Set `CALENDAR_TOKEN_ENCRYPTION_KEY` as a DigitalOcean encrypted runtime variable before enabling the feature. Continue to provide `AUTH_URL`, `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`, and `GOOGLE_WORKSPACE_DOMAIN`. No new redirect URI environment variable is required. Apply `20261006140000_google_calendar_connection`, `20261007120000_google_calendar_event_sync`, and `20261007130000_user_time_zone` in order before running code that queries the connection page. Set a separate random `CALENDAR_SYNC_SECRET` of at least 32 bytes before calling the operational sync route.
4. Google's [Calendar scope guide](https://developers.google.com/workspace/calendar/api/auth) describes the selected scope. Google's [web-server OAuth guide](https://developers.google.com/identity/protocols/oauth2/web-server) documents offline access, incremental grants, state, and redirect URI matching. Google's [verification guidance](https://support.google.com/cloud/answer/13464323) says an app confined to its own Workspace organization, owned by that organization, and configured with an Internal consent screen generally does not require OAuth app verification. If the existing project is External or serves users outside that organization, verification may be required for this scope; confirm the project's actual consent-screen configuration and scope classification before production rollout.

## Event synchronization (Step 2)

`GoogleCalendarEvent` stores one row per Google event ID within a connection and calendar (`connectionId`, `googleCalendarId`, `googleEventId` is unique). With `singleEvents=true`, recurring instances have distinct Google event IDs; `recurringEventId` and `originalStartTime` retain their series identity. UTC `startAt`/`endAt` store timed events, with Google's start/end zone names where supplied. All-day events instead retain date-only `startDate`/`endDate` (Google's end date is exclusive). `GoogleCalendarAttendee` is a separate email-indexed table with original and normalized email, display name, response, organizer and self flags. This supports later matching without duplicating attendees in event JSON. No CRM matching happens during sync.

Only the user's primary calendar is synced in v1. First sync requests an event-overlap window from 60 days before through 90 days after the run time. It expands recurring instances, includes deleted entries, and follows every page. The service upserts each row by Google identity and stores the final `nextSyncToken` only after all pages and local writes succeed. A failed page leaves the old token in place, so retry is safe. Later runs use `syncToken` and page through changes without a date filter. The initial date window is a starting snapshot; subsequent incremental changes can include events outside it. Google's [events.list reference](https://developers.google.com/workspace/calendar/api/v3/reference/events/list) and [incremental sync guide](https://developers.google.com/workspace/calendar/api/guides/sync) define this query and token behavior.

On HTTP 410, the service clears the invalid token and makes a new bounded snapshot. Existing IDs are updated rather than duplicated. Active local rows overlapping the fresh window but absent from that successful snapshot are marked `CANCELLED`; rows outside the window remain as historical source data. A cancelled Google tombstone can contain only an ID, so sync preserves previously stored details and attendee rows while setting `status=CANCELLED` and `cancelledAt`. These rows must be excluded from later Activity review by default. A fresh active version of the same ID clears `cancelledAt`.

Descriptions are not stored. Summary, location, links, organizer, time and attendee metadata are stored only as returned by Google. Private or restricted event details are never inferred; absent fields remain null. Event content and tokens are not logged. Sync does not discard internal-only events, create Activities, generate notifications, or edit Calendar. The Calendar scope remains `calendar.events.readonly`.

**Sync now** in My integrations uses the real signed-in user, including during development impersonation. It can only find that user's connection. The connection row has a 30-minute database lease to avoid concurrent manual and operational syncs. The page shows the last successful sync, latest result and reauthorization requirement without exposing credentials or sync tokens. An `invalid_grant` refresh failure sets `NEEDS_REAUTH`, preserves synchronized events and does not affect normal SalesHub sign-in. Reconnecting with the same Google identity retains sync history and token; disconnect removes the connection and its source events by cascade.

`syncGoogleCalendarConnection()` and `syncAllGoogleCalendarConnections()` are callable server-side. `POST /api/internal/calendar/sync` invokes the latter with a separate `CALENDAR_SYNC_SECRET` bearer secret of at least 32 bytes and returns aggregate counts only. No schedule is installed. A practical starting production cadence is every 15 minutes, subject to observed API quota, sync duration and hosting timeouts. Google watch push can be added later with watch-channel creation, a validated webhook route, resource IDs and channel-expiration renewal; none are needed for this polling-based step. Step 3 remains responsible for Contact/Account and Opportunity/Project matching, review, and any Activity creation.
