# Request / Query Efficiency v2

## Scope and inventory (2026-10-27)

This build follows `../../docs/request-query-efficiency-v1.md`. The main remaining work was Dashboard report duplication, 12 Ownership predicates, quarter Forecast reads, and per-notice expired Price Exception message writes. Recent Dashboard customization can execute saved reports beside built-in reports. Saved report configurations may have distinct filters, grouping, visibility, and metrics, so their executions remain independent. Existing v1 request-scoped identity, eligibility, branding, and module caching remains unchanged.

| Hotspot | Finding | Decision |
| --- | --- | --- |
| Dashboard Pipeline stage and product-category widgets | Both used identical scoped filters and each fetched the same full Opportunity population. | One read, two separate result builders. |
| Dashboard stale Accounts | Hydrated every visible active Account and its latest operational Activity to show a count and five names. | Database count plus five selected IDs/names using the exact recent-activity cutoff. Both reads use one repeatable-read snapshot so the count and preview agree during concurrent edits. |
| Dashboard widget phases | Independent currency, rep, timezone, Forecast, Pipeline, settings, plan-year, and later widget reads waited in several serial phases. | Parallelize only independent reads within the existing phases; retain dependencies on actor, currency, rep IDs, settings, and plan year. |
| Stale saved Dashboard layout recovery | The exceptional recovery path validates up to 24 items one at a time, with at most eight saved reports. Normal layout validation already batches report IDs. | Leave this bounded, uncommon recovery path unchanged; revisit if stale layouts become frequent. |
| Ownership & Reassignment | 12 counts span 12 models and 12 distinct eligibility and lifecycle predicates. They already start in parallel. | Keep 12 Prisma counts. A single SQL statement would duplicate policy predicates and risk divergence from paginated rows and lifecycle preview. |
| Forecast | Team quota targets and Opportunity rows were serial although both use the same period, currency, and actor scope. Forecast page settings were also serial after metrics. | Validate the period and currency before starting either read, then start each independent pair together. Query count remains the same. |
| Snapshot / Movement / Sales Plan history | Forecast Snapshot comparison already batches two runs and their rollups. Movement reads active and archived snapshots in parallel. Sales Plan uses v1 supplied owner IDs. | Retain bounded existing reads and New York capture semantics. |
| Expired PE notices | Message changes with follow-up state, so one `updateMany` per source key was needed by the Prisma path. | One parameterized `UPDATE ... FROM (VALUES ...)` per 200-record evaluator page, preserving each key and message. Transactional single-record sync is unchanged. |

## Query operations and measurements

Counts below are code-path counts for the named operations, not whole-page SQL totals. The reproducible synthetic harness is `node --require ./tests/module-availability-mock.cjs scripts/benchmark-query-hotspots-v2.mjs` from `app`. It creates 1,000 Accounts, 1,000 Opportunities, 2,000 Tasks, 300 PEs, 100 users, and eight quarter markers in memory. Only the Opportunity and PE rows are exercised by its measured cases. A 3 ms asynchronous mock delay models each database round trip. Its wall times are **measured mock timings, not PostgreSQL or browser timings**. No production data was queried or benchmarked.

| Operation | Before | After | Measured mock wall time | Improvement |
| --- | ---: | ---: | --- | --- |
| Two built-in Dashboard Pipeline groupings, 1,000 Opportunities | 2 Opportunity reads | 1 Opportunity read | 85.5 ms → 38.1 ms | Query count and repeated row processing |
| Stale Account widget, 1,000 Accounts | 1 unbounded Account read plus latest Activity relation loading | 1 count plus 1 bounded five-row read in a read-only transaction | Not measured | Bounded result memory; query count may be unchanged or higher depending on Prisma relation strategy and includes transaction control |
| Team Forecast for 100 reps, 1,000 Opportunities | 1 target read then 1 Opportunity read | Same 2 reads, concurrent | Not measured separately | Critical-path latency only |
| Forecast page metrics and settings | 2 serial loader paths | Same 2 paths, concurrent | Not measured separately | Critical-path latency only |
| 300 expired PE messages | 300 individual updates | 2 page updates | 955 ms → 65.5 ms | Write-statement count; after timing includes evaluator work and is therefore conservative, while before timing models only the former update loop |
| Ownership counts | 12 | 12 | Not measured | Semantics retained |

The focused tests assert one Pipeline read with 1,000 Opportunities, concurrent target and Opportunity requests for 100 users and 1,000 Opportunities, no reads on invalid Forecast currency, a shared repeatable-read snapshot for stale Account count and preview, 12 count predicates equal to the corresponding page predicates, and one expired-message statement for 200 PEs. The PE SQL parameterizes every source key and message; its unique source key retains per-record traceability. The SQL touches only unresolved notices and runs after the existing eligibility, preference, create, and obsolete-resolution logic. A failed required statement fails the evaluator rather than returning a partial success result.

The isolated E2E browser smoke measured full-navigation `loadEventEnd` after these changes: Dashboard 654 ms, Ownership 1,915 ms, Forecast 1,895 ms, and Reports 1,510 ms on the second run. Navigation `responseStart` was 520, 1,737, 1,583, and 1,321 ms respectively. These timings use the small seeded E2E database and one Chromium run; no comparable prechange browser capture exists, so they are not before/after claims or scale guarantees. The browser artifact is `navigation-timing.json` from `e2e/performance-smoke.spec.ts`.

## Scope, correctness, and indexes

The shared Pipeline read uses the original actor-scoped `pipelineWhere`; each grouping still applies its own result grouping and currency metrics. Saved reports continue to validate configuration and authorization independently. The stale Account anti-join uses the original operational Activity predicate and `activityDate > now - threshold days`, matching `hasNoActivityInDays` at the exact boundary. It retains Sales ownership scope and returns only five display rows. Its count and preview run in one PostgreSQL repeatable-read transaction to avoid a mixed display when Account or Activity rows change between statements. Ownership predicates still include disabled-module stranded work for Admin; all count and page predicates use the same `ownershipWhere`. Forecast query filters retain actual owner IDs, calendar quarters, currency, stage, category, and operational scope. PE submission-time sync remains inside its existing transaction, including stale-edit and audit behavior.

Request-scoped reuse is limited to the v1 React request/render caches and explicit inputs passed within one Dashboard render. No cross-request actor, role, eligibility, module, domain, or operational owner cache was introduced. The next request still rereads mutable state.

No index or migration is proposed. Existing indexes include `Opportunity(ownerId, expectedCloseDate, currencyCode)`, `Activity(accountId, activityDate)`, Account owner/archival indexes, and the unique Notification source key used by the batched update. Read-only `EXPLAIN` on the isolated E2E database confirmed the PE update SQL: one key used `Notification_sourceKey_key` with an index scan; 200 keys used a hash join against the 200 `VALUES` rows and a sequential scan of about 496 active notices (estimated cost 5.00..25.82). At that small local size the sequential scan is appropriate evidence against a new index. `EXPLAIN ANALYZE` was deliberately not used because it would execute the update. The E2E fixture is smaller than the requested scale scenario, so this plan is not a production latency claim. Reconsider index work only if a representative synthetic database with at least 100,000 unresolved notices shows a 200-key update above 100 ms at p95 or this phase exceeds 10% of evaluator time, and `EXPLAIN ANALYZE` in a rollback transaction shows scan cost dominating after statistics are current. Then compare the existing unique-key index plan against any candidate before requesting migration approval with write and storage cost. These are investigation triggers, not claims that an index will help.

## Remaining scaling thresholds

Revisit the Dashboard Pipeline loader if 1,000-row report populations become materially slower under a real synthetic PostgreSQL run; its full report projection still carries relationships needed for report detail. Revisit stale Account anti-join plans if Account or Activity volumes grow well beyond this scenario. Ownership's 12 parallel counts are a fixed cost; consolidate only if local plans show material latency and a predicate-equivalence test covers every group and lifecycle preview. Ownership rows remain 25 per page with narrow relation selects; Data Quality rows use issue-specific bounded pages and narrow selects. Duplicate Data Quality groups calculate counts separately, but do not hydrate full results. Deep offset pages were not benchmarked at extreme synthetic depths, so offset pagination remains. Forecast Snapshot and Movement pages retain their current 104/200-row bounds. The mock figures above do not establish PostgreSQL latency at scale.

No Redis, CDN CRM-data cache, materialized view, queue, read replica, pooler change, worker, persistent process cache, schema change, CI trigger change, or new product behavior was added.
