# Generic Configuration v1

`DeploymentBranding` is a typed singleton for the user-facing Company Name, Product Name, and nullable logo object reference. Missing rows use BIXOLON America, Inc., SalesHub, and the bundled BIXOLON PNG. Names are separate from business records and internal repository/package identifiers. An Admin can edit them without redeploying. Sign-in, navigation, Dashboard, Help, selected Admin copy, search, and Sales Plan export filenames use the configured names. PNG, JPEG, and WebP logos up to 1 MB are signature checked and stored in the private object store's dedicated `branding/` path. The public logo route reads only the currently configured key, returns the validated MIME type with `no-store`, and has no key parameter. Replacing or resetting a logo deletes the former object after the database update; failed deletion is logged for operational cleanup.

`TrustedSignInDomain` stores lowercase domain keys and active state. If it has no rows, valid `GOOGLE_WORKSPACE_DOMAIN` supplies the bootstrap policy. The first Admin mutation inserts that domain in the same serialized transaction. Once any row exists, the environment value is no longer an implicit grant. Deactivation must leave another active domain. A current-domain deactivation requires an explicit warning acknowledgment. The sign-in callback and linked-session resolution read active rows without a long-lived cache. Google verified email, signed hosted-domain claim, approved active User, and issuer/subject link remain mandatory. Roles are assigned to Users independently from domain or language.

Trusted sign-in domains are **not** a general list of internal email domains. Organization Identity v1 adds a separate typed `InternalEmailDomain` list for Calendar, My Day, and Support classification. The lists can differ; a trusted domain alone does not become internal once Admin-managed internal rows exist. See [Internal Email Domains](internal-email-domains.md).

Next.js root metadata and `app/icon.png` remain static in v1 to avoid making metadata depend on runtime database access. A future build may evaluate dynamic browser metadata after measuring build and cache behavior. Tenants, SSO alternatives, and custom roles are outside v1. The next approved deployment-level setting, [Optional Module Visibility v1](optional-module-visibility-v1.md), uses its own typed table rather than adding module choices to branding or sign-in domains.
