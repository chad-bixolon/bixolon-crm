# SalesHub release checklist

This is the maintainer entry point for deciding whether a reviewed commit can be deployed. The release checker validates local code; the external checks below are still required. It never deploys, pushes, changes production configuration/data, reconnects providers or applies production migrations.

The current runtime pin is **Node.js 22.23.4 LTS**, the [October 21, 2026 security release](https://nodejs.org/en/blog/release/v22.23.4/). `app/.nvmrc` and both Docker base images use this patch; the package engine minimum is `>=22.23.4 <23`, which the release checker enforces. Keep SalesHub on Node 22 LTS. Older version numbers in dated validation records describe historical runs, not the current runtime requirement.

1. Review the candidate and start from a clean worktree. Select the installed Node runtime in `app/.nvmrc` (supported range: `app/package.json`), install locked dependencies using the existing setup, and ensure Docker/Compose, Python 3 and the existing Chromium/library caches are available. No runtime, dependency or browser downloads happen automatically, except the existing migration image build when needed. See [browser prerequisites](browser-e2e.md).
2. From `app/`, run **`npm run release:check -- --base <last-deployed-commit>`**. For a single-commit candidate the default baseline is `HEAD^`. For a release containing several commits, explicitly supply the last deployed commit: using the default would only inspect the last commit for migration changes. Baselines must exist locally; no fetch occurs. Optional `--focus support` or `--focus snapshots` adds a small existing regression group.
3. Require `READY FOR RELEASE` and review `reports/release/<UTC-time>-<pid>/release.txt`, `release.json` and stage logs. They are ignored, private local evidence, retained on both success and failure; copy the reviewed evidence to the release/incident record as appropriate. Unit skips are visible. A failed stage stops subsequent stages, exits nonzero and records NOT RUN results. `--allow-dirty` is for developing the checker or validating uncommitted work: it runs checks but **always reports NOT READY**. Re-run on the final clean commit before deployment. No bypass turns failed or skipped required checks into READY.
4. When `prisma/schema.prisma`, `prisma.config.ts` or `prisma/migrations/` changes, the checker builds the existing disposable migration-test image from the current candidate, then runs `scripts/test-migrations.py`: fresh replay, populated preservation, integrity, rollback and schema parity. It never runs production checksum/status scripts against a live database. Review SQL, verified backups, expected pending migrations and production verification separately via [migration operations](migration-operations.md), [foundation procedure](foundation-migration-review.md) and [deployment preparation](deployment.md#database-migrations).
5. Follow [DigitalOcean deployment verification](deployment.md#digitalocean-app-platform-expectations). Confirm deployed revision, migration status, generated-client/runtime alignment, `/api/health`, normal Google sign-in and representative authenticated pages after deployment. Local credentials-based browser auth does not prove production Google OAuth or provider state.
6. Verify the [Weekly Snapshot scheduled Job](../../docs/weekly-snapshot-automation.md#digitalocean-production-configuration-after-reviewed-deployment), [daily notification scheduler](notification-center.md#operation), and [Calendar polling](google-calendar-connection.md). Check recent execution evidence in [System Health](system-health.md); code deployment does not install schedules. Confirm env variable **names/configuration**, never copy secret values into release evidence.
7. Check [Support Gmail rollout/configuration and recovery](support-email-rollout.md), [Calendar OAuth setup/recovery](google-calendar-connection.md) and [private document storage](document-attachments.md) where enabled. The checker uses mocked/local providers and makes no live Gmail/Calendar calls.
8. Before promoting, identify the previous working release and verified backup. Follow [Support rollback/recovery](support-email-rollout.md#rollback-and-recovery), [snapshot recovery](../../docs/weekly-snapshot-automation.md), and [database/storage recovery guidance](deployment.md#local-docker-storage-and-dependency-recovery). An app rollback does not reverse schema changes or restore a database automatically; preserve newer CRM work.

## What the command runs

Repository identity/status → supported Node/npm and pinned Prisma versions → existing safe Prisma generation plus Prisma-normalized generated-schema/embedded-runtime comparison → existing lint → existing typecheck → existing unit suite (two file workers) → migration checks when applicable → optional focused browser checks → three release-smoke browser tests → **one** `npm run build -- --webpack` → unchanged-candidate content fingerprint/diff check → evidence summary.

Webpack is the reliable production validation path on this host: Turbopack has repeatedly failed to bind its local worker ports. This changes neither the normal build command nor Docker/deployment behavior. Schema normalization runs on a small run-owned copy using the installed Prisma formatter; tracked schema files are never formatted. Generated Next.js config edits from the build are restored to their starting contents. The generated Prisma client is refreshed in ignored `node_modules`, without connecting to a database or modifying tracked generated files.

The compact smoke suite covers the sign-in screen/local authenticated shell, Account detail and a real isolated phone-number edit/save, Opportunity detail/edit, Task detail/edit, Support Case detail/edit as Support, Reports, an Admin settings page and Help. It reuses the guarded local E2E server/seed with the dedicated `saleshub_e2e_release` database, one Chromium worker, zero retries, installed browser caches, and mocked providers. Fixed smoke fixtures reset their edited field each run. No full browser suite runs by default; use module regressions for larger feature changes.

## Host hygiene and future CI

Run only one release check at a time; a checkout-local lock prevents overlapping release checks. If a process is forcibly killed, inspect `reports/release/.active/owner.json` and remove only the confirmed abandoned lock. Do not run the check alongside another build or Playwright server on port 3100. Validation refuses to start with less than 1 GiB free in its worktree/temporary filesystem. It streams subprocess output into per-stage evidence logs (with credential redaction), retains failure screenshots/traces, and removes its own temporary directory and successful browser artifacts. It leaves normal `.next` build output, reusable browser caches, and the existing E2E Postgres service/volume available. It never prunes Docker/containerd, removes volumes or copies large caches. Review old evidence directories deliberately when space is low; failures remain available for diagnosis.

No hosted CI workflow is added. Future CI can select the pinned Node runtime, provision the same Docker/Compose/Python/browser prerequisites, install locked dependencies, check out both candidate and baseline commits, run this same command on a clean tree, and upload `app/reports/release/` as a protected artifact even on failure. Production credentials are unnecessary. External deployment, schedules and provider verification remain separate maintainer steps.
